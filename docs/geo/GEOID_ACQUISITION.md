# GEOID_ACQUISITION — KNGeoid24 격자 확보·변환·검증 기록

> 목적: risk `geoid-grid-provenance-unverified`(정본: `.ksi/goals.json`)의 해소 조건
> "국토지리정보원 정식 경로 취득 + 통합기준점 실측 대조 통과" 진행 상황을 정직하게
> 기록한다.
>
> **결론 요약(TL;DR)**: 정식 경로로 KNGeoid24 격자를 취득했고, GeoTIFF 변환·격자
> 노드 정확도는 실측으로 확인했다(오차 ~1e-11m, float64 반올림 수준). 첫 시도
> (§5)의 통합기준점 실측 대조는 좌표 정밀도가 낮은 대체 데이터셋(≈1.1km급)만
> 접근 가능해 합격선(≥5점, ≤0.05m)을 충족하지 못했다(9점 중 2점만 통과).
> **이후 `map.ngii.go.kr` 정식 조서(mm급 통합기준점 성과)로 재시도한 대조(§6,
> 2026-08-12)는 전국 10개 시도에 분산된 10점 전부 PASS**(최대오차 0.0401m,
> RMSE 0.0247m)했다 — §5 의 미달이 격자·변환의 결함이 아니라 그때 썼던
> 벤치마크 데이터셋의 좌표 정밀도 문제였다는 §5.3 의 진단을 뒷받침한다.

## 2. 포맷 실측 확정 (추측 배제, 숫자로 검증)

### 2.1 `.gri`

- 헤더: `32.000000 42.993920 123.000000 131.998000 0.0163600 0.0163600`.
- `rows = round((42.99392-32.0)/0.01636)+1 = 673`, `cols = round((131.998-123.0)/0.01636)+1 = 551`.
- 파일의 헤더 이후 숫자 토큰 개수 = 370,823 = 673×551 — **정확히 일치**(포맷 확정).
- 값 배열을 "0행=최북단(위도 내림차순), 각 행은 서→동(경도 오름차순)"으로 재구성한
  뒤 유효값(9999 아님)의 위경도 범위를 뽑으면 `32.99796~39.00208`(위도),
  `123.99796~131.998`(경도) — 이는 아래 `.dat` 파일의 범위와 **정확히 일치**한다.
  즉 `.gri` 는 정수 위경도 경계(32~43°N, 123~132°E)로 패딩된 더 넓은 사각형에
  같은 유효 데이터를 담고, 남는 자리를 9999(nodata)로 채운 것이다.
- nodata 비율 51.4%(370,823개 중 190,503개) — 절반이 패딩.

### 2.2 `.dat`

- 180,320행, 전부 `lat lon N` 3열. 고유 위도 368개 × 고유 경도 490개 = 180,320 —
  **완전 직사각형**(결측 없음). 간격 0.01636°(위경도 동일).
- 위도 32.99796~39.00208, 경도 123.99796~131.99800, N 15.068~33.623m.

### 2.3 두 포맷의 관계 — 실측으로 확인(추측 아님)

무작위 15개 좌표를 두 파일에서 각각 찾아 대조한 결과 **오차 0.000m로 전부 일치**
(`tools/convert_geoid_grid.py` 개발 중 직접 실행해 확인, 재현 가능).

이 사실은 중요하다 — `references/repos/ksi-terra/docs/GEOID_ACQUISITION.md` 는
KNGeoid18 패키지에 동봉된 동일 크기·동일 헤더의 `.gri` 파일(`hybrid_geoid.gri`,
3,870,498 bytes로 이번 KNGeoid24 `.gri` 와 바이트 크기까지 같다 — 단, sha256은
다르므로 동일 파일은 아니다)을 "보정 전 원시 중력지오이드 격자로 추정, 프로덕션에
연결하지 않음"이라고 적었다. **이번 KNGeoid24 실측 대조는 그 추정이 이 파일에는
적용되지 않음을 직접 반증한다** — `.gri`·`.dat` 는 같은 최종(보정 후) 지오이드고
값의 두 가지 포장(하나는 정사각 패딩, 하나는 유효범위만 나열)일 뿐이다. 다만 이는
**이번 KNGeoid24 배포분에 한한 실측 확인**이며, NGII가 모든 버전·모든 배포에서
같은 관례를 쓴다고 일반화하지는 않는다(확인 필요 시 재현 절차: 아래 §4).

## 3. GeoTIFF 변환

- 스크립트: `tools/convert_geoid_grid.py` (신규, 독립 구현 — references/ 코드를
  복사하지 않았다. CLAUDE.md 참조).
- **기본 산출물은 `.dat`(3열) 쪽을 변환한다** — nodata 패딩이 없어 "9999를 실수로
  유효값처럼 보간" 사고 여지가 구조적으로 없고, 국내 유효 범위만 정확히 담는다.
  `.gri` 변환은 교차검증에만 썼다(§2.3).
- 픽셀 중심 규약: 입력 좌표가 이미 셀 중심이므로 GeoTIFF 원점은
  `west=lon_min-dlon/2, north=lat_max+dlat/2` 로 반 셀 이동 — 이는
  `packages/geo-spatial/src/ksi_geo_spatial/vertical.py`
  `GeoidGrid.height_at()`가 조회 시 되짚는 `-0.5` 오프셋과 대칭이 맞아야 한다(그
  독스트링이 이미 이 규약을 명시하므로 변환기도 같은 규약을 따랐다).
- nodata: 원본 관례값 9999.0 을 배열 안에서 **NaN**으로 바꿔 쓰고 GeoTIFF
  nodata 태그도 NaN 으로 설정한다(리터럴 9999.0 을 그대로 쓰면
  `GeoidGrid.height_at()`의 finite 검사를 우연히 통과해 nodata 경계 부근에서
  9999 를 섞은 보간값을 조용히 반환할 위험이 있다 — `.dat` 산출물은애초에 nodata가
  없어 이 문제 자체가 없다).
- 산출물: `data/geoid/KNGeoid24.tif`(EPSG:4326, 단일밴드 float64, nodata=NaN,
  368×490).

### 3.1 변환 검증 — 원본 대비 격자 노드 정확도(실행 로그, 2026-08-12)

`tools/convert_geoid_grid.py --input data/geoid/raw/KNGeoid24.dat --format dat
--output data/geoid/KNGeoid24.tif --verify-samples 20` 실행: 원본에서 무작위
추출한 20개 격자 노드를 변환된 GeoTIFF 를 `GeoidGrid`(운영 코드 그 자체)로 다시
조회 — **최대오차 1.10e-11m**(float64 반올림 수준, 사실상 완전 일치). `.gri` 쪽도
동일 스크립트로 변환·검증해 최대오차 9.37e-12m — 두 포맷 모두 변환기가 값을
왜곡하지 않음을 확인했다.

```bash

    --input data/geoid/raw/KNGeoid24.dat --format dat \
    --output data/geoid/KNGeoid24.tif --verify-samples 20

export KSI_GEOID_GRID="$(pwd)/data/geoid/KNGeoid24.tif"
```

환경변수를 직접 읽는다(코드에 경로를 하드코드하지 않는다 — 미설정=정표고 미사용,
설정했는데 파일 없음=오류, 두 경로가 다르게 처리되는 기존 설계 그대로).

### 5.3 원인 진단(추정, 확진 아님)

이 결과는 `references/repos/ksi-terra`가 **같은 데이터셋·같은 방법론**으로
KNGeoid18 을 대조했을 때의 결과(3/9 PASS, 최대오차 7.93m, RMSE 3.09m)와
정성적으로 거의 같다 — 특히 id 7·10 이 양쪽 다 4~8m급으로 크게 튀는 점까지
일치한다. 이는:

1. **격자·변환의 결함이 원인일 가능성은 낮다** — 같은 좌표 오류 패턴이 서로 다른
   지오이드 모델 버전(18 vs 24)에서 재현되므로, 오차의 지배적 원인은 지오이드
   모델이 아니라 **이 CSV 자체의 좌표 정밀도(≈1.1km)와 개별 행 오기재**로 보인다.
2. 이 CSV는 정식 통합기준점망이 아니라 항공사진 촬영용 민간 임시 GPS 기준국
   조서라, 정표고 값이 정밀 수준측량으로 결정됐다는 보장이 없다.

**결론**: 이 경로만으로는 합격선을 충족하지 못한다. §5.1 의 "국가기준점_20250428"
경로(로그인 후 정식 통합기준점, 고정밀 좌표)로 재시도가 필요하다 — 이 문서는
그 재시도를 완결로 선언하지 않는다.

> **후속(§6)**: 위 "재시도가 필요하다"는 §5.1 경로(`map.ngii.go.kr` 정식 조서)로
> 2026-08-12 같은 세션 내에서 재시도했고, 10/10 PASS로 합격선을 충족했다. 아래
> §5 의 기록은 그 실패 원인 진단(§5.3)이 옳았음을 보여주는 대조군으로 그대로
> 남긴다 — 삭제·수정하지 않는다.

## 6. 통합기준점 정식 재대조 (2026-08-12, `map.ngii.go.kr` 조서)

### 6.1 경로

§5.1 이 미접근으로 남겼던 "국가기준점_20250428" 경로(`map.ngii.go.kr/pd/ctlsSvc/ctlsSvc.do`)를
대표자가 이미 로그인해 둔 Chrome 세션(claude-in-chrome MCP, 새 탭)으로 재시도했다.
로그인 여부는 화면 우상단 "로그아웃" 표시로 확인만 했고, 로그인 시도는 하지
않았다(규칙 준수). 자료실 > 지도자료 > 카탈로그 > "국가기준점" 탭 > 점의종류
드롭다운 "통합기준점" 선택 후 검색 → 전국 **5,144점**(515페이지, 페이지당 10개)이
조회됐다.

### 6.2 표본 선정

`data/geoid/KNGeoid24.tif` 를 `rasterio`로 직접 열어 확인한 유효 데이터 범위
(2026-08-12): 위도 **32.98978~39.01026**, 경도 **123.98978~132.00618**
(nodata 제외, `bounds`는 패딩 포함 격자 전체 경계와 거의 같음 — §2.1 의 헤더값과
정합).

이 범위 안에서 지역적으로 최대한 분산시키기 위해, 페이지 번호를 순서대로 넘기는
대신 검색창의 **"시도" 필터**를 바꿔가며 각 시도의 검색 결과 중 한 점(대개 1번
행)을 선택했다 — 같은 도엽에 몰리는 것을 피하기 위한 선택이다. 순서대로
서울특별시 → 인천광역시 → 충청남도 → 전북특별자치도 → 전남광주통합특별시 →
경상북도 → 경상남도 → 부산광역시 → 제주특별자치도 → 경기도, 총 10개 시도에서
1점씩 골랐다.

**강원특별자치도는 같은 방식으로 조회하면 0건**이었다(시도 드롭다운에 항목은
있으나 이 "통합기준점" 데이터셋에는 강원 소재점이 없는 것으로 보임 — 원인은
확인 필요, 이 세션에서 재현됨). 그 자리를 경기도로 대체했다.

각 점은 목록의 "조서보기" 버튼을 눌러 뜨는 공식 조서(PDF 뷰어) 모달에서
위도·경도(DMS)·타원체고·표고·지오이드고를 스크린샷으로 직접 읽어 기록했다(추측·
생성 없음 — 아래 표가 그 값 그대로다). 다음 표는 검증 재현을 위해 점의번호를
함께 남긴다.
