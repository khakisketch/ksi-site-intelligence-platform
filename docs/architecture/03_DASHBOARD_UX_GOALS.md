> 착수 게이트 산출물(CLAUDE.md "작업 방식"). `02_SERVICE_BLUEPRINT_AND_UX.md`의 개념을 이 문서가
> 측정 가능한 목표로 구체화한다. 이 문서가 `/ui-audit`의 측정 기준이다.

> 홈·이벤트 트리아지·임무·현장 + 현장등록/새 조사 Wizard. MASTER_PRD §7의 2D/3D World·

## 1. 타깃 페르소나 (PRD §4.1 중 S3 범위)

S3가 노출하는 화면(홈/현장/임무/이벤트+Wizard)에 실제로 닿는 역할만 1차 대상으로 삼는다.
나머지 역할(공사관리자·점검자·본사관리자·AI/Data 관리자)은 자산점검·2D3D World·보고서·Fleet
화면이 필요해 후속 S에서 다룬다.

| 페르소나 | 핵심 업무(S3 범위) | 줄이려는 것 |
|---|---|---|
| **현장소장** | 홈에서 현장 상태·미조치 위험을 한눈에, 현장 상세에서 상태 이력 확인 | 여러 도구·비정형 보고서 취합 |
| **안전관리자** | 이벤트 트리아지(확정/오탐/배정), 이벤트 상세에서 위치·증거 검토 | 영상 상시시청, 수동 위험 판단 |
| **드론 운영자** | 새 현장조사 Wizard로 임무 계획 검토·승인, 임무 목록에서 발급 이력 확인 | 웨이포인트 수동설정, 계획 재작성 |

부 페르소나: **현장 등록 담당자**(현장소장 겸임 가능) — 현장등록 Wizard로 최초 온보딩.

"핵심 산출물까지 N클릭" — 데스크톱 사이드 네비게이션 기준, 로그인 이후.

| 동선 | 핵심 산출물 | 예산 | 경로 |
|---|---|---|---|
| 콜드스타트 최초 현장 등록 | Baseline Mapping 임무 계약 발급 완료 | Wizard 8스텝(PRD §7.3 구조 유지, 스텝 자체가 예산) | 홈/현장 → "현장 등록" → 8스텝 → 발급 완료 화면 |
| 일상 이벤트 확인 | 이벤트 확정/오탐 판정 | 3클릭 | 홈(검토필요 이벤트 카드) → 이벤트 상세 → 확정/오탐 버튼 |
| 새 현장조사 실행 | Mission Contract 발급 | 5클릭(PRD §7.4 5스텝 = 예산 그 자체) | 현장 상세 → "새 조사" → 5스텝 → 발급 완료 |
| 임무 이력 조회 | 특정 임무의 계약/산출물 확인 | 2클릭 | 사이드 "임무" → 목록에서 항목 클릭 |
| 현장 상태 확인 | 현재 상태·최근 전이 사유 | 2클릭 | 사이드 "현장" → 목록에서 항목 클릭 |

Wizard 두 개는 PRD가 이미 스텝 수를 못박았으므로(§7.3=8, §7.4=5) 예산은 "그 스텝 수를 넘기지
않는다"이지 더 줄이는 것이 목표가 아니다. 스텝 내 이탈(뒤로가기·임시저장) 시 입력이 소실되지
않아야 한다(재작업 비용이 Wizard 완주율을 결정).

## 3. 필수 상태 인벤토리

화면마다 아래 5축을 모두 설계 단계에서 명시한다. 빠뜨린 축은 `/ui-audit`가 결함으로 잡는다.

### 3.1 빈 상태 (empty)
- 현장 0개(콜드스타트 최초 진입) — 홈·현장 목록 모두 "현장 등록" CTA로 탈출구 제공, 빈 화면만
  두지 않는다.
- 이벤트 0개 — "검토할 이벤트가 없습니다" (침묵이 아니라 명시적 문구 — 로딩 실패와 구분 필수).
- 임무 0개 — 현장은 있으나 임무 미발급.

### 3.2 희박 상태 (sparse)
- 현장 1개, 이벤트 1~2개 — 카드/리스트가 빈 공간을 어색하게 채우지 않는지(레이아웃이 1건에서도
  깨지지 않는지).

### 3.3 긴 텍스트 / 한글
- 현장명 20자 이상(예: "○○산업단지 3공구 신축공사 현장(임시)") — 카드·목록·Wizard Step1에서
  줄바꿈이 단어 중간에서 끊기지 않는다(`word-break: keep-all`).
- 이벤트 전이 `reason`/`evidence` 자유 텍스트가 긴 경우 — 상세 화면은 전문 노출, 목록은 말줄임.
- Wizard의 AOI 폴리곤 꼭짓점이 많을 때(최대 256) 지도 그리기 UI 성능.

### 3.4 에러
API 에러 코드를 그대로 노출하지 않고 사람 말로 번역한다(§4 마이크로카피 SSOT와 결합):
- `401` — 세션 만료, 재로그인 유도(원래 화면으로 복귀 가능해야 함).
- `403` — 권한 없음, "이 작업은 OO 권한이 필요합니다"(어떤 권한인지 명시 — 막연한 "접근 불가"
  금지).
- `404` — 대상 없음(현장/이벤트/임무) — 목록으로 복귀 링크.
- `409` — 충돌(예: `DUPLICATE_SITE_ID`, `ILLEGAL_TRANSITION`, `MISSION_ID_CONFLICT`) — 왜
  막혔는지와 현재 실제 상태를 함께 보여준다(막연히 "실패"만 띄우면 사용자가 같은 행동을
  반복한다).
- `422` — 입력 검증 실패(`INVALID_SITE`, `EVIDENCE_INCOMPLETE`, `COVERAGE_BELOW_CONTRACT_PROMISE`
  등) — 필드 단위로 지적.
- `503` — `STORE_UNAVAILABLE` — "서버 저장소 점검 중, 잠시 후 다시 시도" + 재시도 버튼(Retry-After
  존중). **INV-040**: 이 상태를 데모 데이터나 캐시로 가려 정상처럼 보이게 하지 않는다.

### 3.5 로딩
- 목록/상세 진입 시 skeleton(레이아웃 점프 방지) — spinner 단독 금지(콘텐츠 크기를 예고).
- Wizard Step 4(자동 계획 검토) 서버 계산 대기 — 발급 실패 가능성이 있는 단계이므로 로딩과
  실패를 같은 자리에서 명확히 구분.

### 4.6 확인(Acknowledge) SLA — 정본 (2026-08-04 대표자 확정)

이 값은 화면에 "목표 15분 안에"로 노출되므로 **제품 약속**이다. 그래서 코드가 아니라 여기가
정본이고, `apps/dashboard/src/lib/core-api/triage.ts` 의 `ACK_SLA_MS` 가 이 표를 따른다.

시계는 둘이다. 여기서 정하는 것은 **확인 시계뿐**이다.

- **확인(Acknowledge)** = 감지가 진짜인지 사람이 판단하기까지 (status: 관측 → 확정/오탐)
- **조치(Resolve)** = 확정된 위험을 실제로 제거하기까지 (triage: 배정 → 해결)
  — 확정 건이 아직 없어 측정할 대상이 없다. **미정으로 남긴다.**

| Severity | 확인 목표 |
|---|---|
| CRITICAL (위험) | 15분 |
| HIGH (높음) | 1시간 |
| MEDIUM (보통) | 4시간 |
| CANDIDATE (후보) | 24시간 |
| **미판정 (severity=null)** | **4시간** |

근거는 위험성평가 4등급(즉시 작업중지 / 즉시·단기 개선 / 계획적 개선 / 자율)과 건설 안전 SaaS
통상 기본값이다.

**미판정 항목이 이 표에서 가장 중요하다.** 등급별 SLA 만 두면 판정 전 이벤트에는 어떤 목표도
걸리지 않아 영원히 방치돼도 신호가 없다. 그런데 판정 전에는 그게 CRITICAL 인지 오탐인지 알 수
없으므로, **모르는 것을 오래 두는 것이야말로 가장 위험하다.** 현재 인지 파이프라인이 severity 를
채우지 않아 실데이터는 사실상 전부 이 경로를 탄다 — 예외가 아니라 기본값으로 설계한다.

`due-soon`(목표의 80% 경과)에서 미리 경고한다. 초과하고 나서야 빨개지면 예방이 아니라 사후 통보다.

## 5. 접근성 예산

> **2026-08-04 개정 (대표자 결정).** 개정 전 조항("본문 최소 16px, 상태 라벨류도 14px 미만
> 금지", "터치 타겟 ≥ 44×44px" 무조건)은 승인된 잉크 모노크롬 시안(본문 14px · 배지 11.5px ·
> 버튼 38px · nav 항목 34px)과 정면으로 충돌했다. 구현은 시안 편에 서 있었고, 이 문서는
> 그대로여서 `/ui-audit` 이 매번 같은 실패를 냈다. **시안 밀도를 정본으로 채택하고, 접근성은
> 크기 하한이 아니라 입력장치 분기로 지킨다**는 쪽으로 정리한다.
>
> 근거: 44px 규칙은 손가락 때문에 있는 것이지 픽셀 때문이 아니다. 마우스 환경까지 44px 로
> 묶으면 계측 도구가 문서처럼 헐거워져 한 화면에 들어가는 사실의 개수가 줄어드는데, 그건
> 이 제품에서 곧 쓸모의 감소다. 반대로 이 제품의 1급 기기인 태블릿 가로는 실제 터치라
> 44px 가 그대로 필요하다. 그래서 크기를 고정하지 않고 `pointer` 로 나눈다.

- **터치 타겟**: `pointer: coarse`(태블릿·폰)에서 ≥ 44×44px, `pointer: fine`(마우스)에서 ≥ 36px.
  구현은 `globals.css` 의 `.tap-target` · `.btn` · `.input` 이 이 분기를 담당한다 — 화면 코드에서
  `min-h-11` 을 직접 쓰지 말고 이 클래스들을 쓴다(직접 쓰면 분기가 깨진다).
- **타이포 하한**: 본문 14px · 보조 텍스트 12.5px · 배지/카운터 11.5px · eyebrow 10.5px.
  10.5px 미만은 금지. 본문 14px 는 `body` 에 걸려 있고 Tailwind 유틸리티는 rem 기준이라
  영향받지 않으므로, 화면 코드는 `text-[13px]` 처럼 명시적으로 쓴다.
- 대비 AA 이상 — 특히 Severity/Status 배지 색상(색맹 고려 — 색만으로 구분하지 않고 라벨 텍스트
  병기 필수, PRD가 이미 라벨 병기를 전제).
- **다크 모드는 현재 비활성**(2026-08-04 결정). `prefers-color-scheme` 자동 활성을 끊고
  `:root[data-theme="dark"]` 로 옮겼다 — 색이 의미를 갖는 유일한 자리(안전 상태색)의 다크 대비가
  실측된 적이 없어서다. 재활성 조건은 `globals.css` 해당 블록 주석에 적혀 있다.
- 태블릿 현장 어휘 — 현장 실사용자가 태블릿을 주 기기로 쓴다(전역 CLAUDE.md 근거).
  `md:` 분기가 본문을 폰보다 좁게 만드는 실수를 피한다(768 뷰포트 필수 검증).
- **레이아웃 1급 뷰포트는 태블릿 가로(1024)다.** 시안 `design/ksi-site-intelligence/index.html`
  주석이 정본: 1280+ 사이드바 216px · 1024~1279 176px · ~1000 1열. 본문에도 `lg:`/`xl:` 열
  구조를 부여한다 — `max-w-*` + `mx-auto` 로 데스크톱에서 가운데 좁은 문서가 되는 것은 결함이다
  (로그인 카드처럼 본래 좁아야 하는 것은 예외).

## 6. 네비게이션 스코프 (PRD §7.1 taxonomy 유지, 구현은 S3 범위만)

데스크톱 사이드 10항목·모바일 하단 5탭의 **명칭과 순서는 PRD 그대로 유지**한다(향후 S가 항목을
채울 때 재배치하지 않기 위해). S3에서 실화면으로 연결되는 항목과 그렇지 않은 항목을 구분한다.

- 실구현(S3): 홈, 현장, 임무, 이벤트
- 자리만 유지, 클릭 시 "준비 중" 안내(더미 라우트 아님 — 링크 자체를 숨기지 않고 상태를
  정직하게 보여준다, INV-040과 동일한 정신): 자산·시설물, 2D·3D World, 보고서, Fleet·Edge,
  Data·AI, 설정
- 모바일 "더보기"는 위 미구현 항목 + 설정 진입점.

## 7. 구현 노트 (착수 후 확정된 결정 — 재작업 방지용 기록)

- **인증**(2026-07-30 갱신 — goal `dashboard-operator-login`): 백엔드에 사용자 관리·토큰
  발급 API는 없다(사전 프로비저닝된 bearer token만 존재, `scripts/run_core_dev.py` 참조).
  §8에 적었던 "S3는 로그인 화면 비범위, 단일 운영자 토큰을 서버사이드 env로 주입" 결정은
  risk `dashboard-unauthenticated-signing-proxy`(대시보드 포트에 도달 가능한 누구나 고정
  ADMIN 권한으로 쓰기 요청 가능)로 이어져 폐기됐다. 대시보드는 이제 `/login` 화면에서
  운영자가 자신의 사전 프로비저닝 토큰을 직접 입력하고, 그 토큰을 httpOnly 세션 쿠키에
  담아 이후 요청에 싣는다(ADR-KSI-008 §2가 애초에 의도한 "S3 대시보드 로그인도 이 토큰으로
  시작"). 토큰은 여전히 Route Handler/Server Component에서만 쓰고 브라우저 JS로 내려보내지
  않는다. 각 운영자는 자신의 role 권한으로만 Core에 도달한다(§도메인 불변식 role↔permission
  표 SSOT는 `services/core/src/ksi_core/auth.py`). risk `dashboard-wizard-rbac-mismatch`
  (비-ADMIN role의 Wizard 권한 정합)는 ADR-KSI-015(역할 3개 축소: `ADMIN`·`FIELD_OPERATOR`·
  `VIEWER`)로 해소됐다 — `SITES_WRITE`를 가진 역할은 이제 항상 `MISSIONS_ISSUE`도 가져
  통합 Wizard가 반쪽 상태를 만들지 않는다. "등록만 먼저"는 이제 권한 분기가 아니라
  `/sites/new`에서의 사용자 선택이다(도메인상 `UNMAPPED`가 정상 중간 상태이기 때문 — RBAC
  결함의 흔적이 아니다).
- **캐싱**: Next 데이터 캐시에 기대지 않는다 — 모든 Core API 호출은 `cache: "no-store"`.
  운영자가 현장/이벤트/임무 최신 상태를 즉시 봐야 하므로 staleness 허용치가 낮고, MVP
  트래픽 규모에서 캐시 계층의 이득보다 정합성이 우선한다.
- **미션 발급 고급 파라미터**(`viewpointPolicyId`/`riskPolicyPackId`/`fallbackPolicyId`/
  `capturePolicyId`/`droneEnumValue` 등)는 백엔드에 해석 레지스트리가 없다(openapi 주석:
  "M4D 값은 실기 검증 전 서버가 추측하지 않는다"). Wizard는 이 값을 그럴듯한 드롭다운으로
  꾸미지 않고 "고급 설정" 섹션에 명시적 텍스트 입력 + 설명 문구로 노출한다(INV-040 정신 —
  모르는 것을 아는 것처럼 보이지 않는다).
- **미션타입→경로패턴 제약**(`services/core/src/ksi_core/mission_plans.py`): lawnmower(매핑
  계열, `spacingM` 필수) = BASELINE_MAPPING·SPATIAL_REFRESH·SURVEY_GRADE_MAPPING·
  PROGRESS_CAPTURE·UNIFIED_SITE_SURVEY. perimeter(순찰 계열) = AUTONOMOUS_PATROL·
  INCIDENT_SURVEY. 그 외(ASSET_INSPECTION 등)는 422 거부 — 새 현장조사 Wizard의 "목적"
  스텝은 이 제약을 벗어나는 PRD §7.4 목적(구조물 결함·장비·자재 현황)을 "준비 중"으로
  비활성 표시한다(허용되지 않는 조합을 시도해보고서야 오류를 보여주지 않는다).
- **현장등록 Wizard 8단계 중 실동작 없는 단계**: 4단계(BIM/도면 가져오기)는 업로드
  파이프라인이 없어 "이 버전에서는 지원하지 않습니다" 안내 후 건너뛰기만 제공한다. 8단계
  (자율운영 활성화)는 실기 비행·검증 없이는 실제로 활성화할 것이 없으므로 "완료 요약 + 다음
  단계 안내"로 대체한다 — 라벨을 유지하되 하지 못하는 것을 하는 척하지 않는다. 두 경우 모두
  PRD의 8단계 구조(step budget)는 유지한다.
