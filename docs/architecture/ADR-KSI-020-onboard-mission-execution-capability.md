# ADR-KSI-020 — 온보드 임무 실행 능력의 실재 확인, 그리고 그것을 쓰지 않기로 하는 결정

- 상태: ACCEPTED (2026-08-15, 대표자 지시)
- 2026-08-26 대표자 개정: FIELD-0a 이전 전면 신규 기능 동결은 해제한다. 다만
  비행 실행 단계와 장비 capability 검증 게이트는 해제하지 않는다. 사전 구현된
  adapter나 SDK 빌드는 지원 증거가 아니며, HIL 전에는 `NOT_VERIFIED`와 feature
  flag OFF를 유지한다(ADR-KSI-023/027 개정 참조).
- 관련: ADR-KSI-019(관측 자율성 3단계 — 본 ADR이 그 §4 G3·D4를 정정한다),
  ADR-KSI-004(DJI 연동 이원화), ADR-KSI-006(온보드 기동), ADR-KSI-016 D6(정확도 등급),
  `docs/dji/12_CLOUD_API_WAYLINE_DISPATCH_RESEARCH.md`(범위 한정됨, §2),
  risk `dji-pilot-cloud-wayline-support-conflicting-docs`
- 본 ADR은 **능력의 실재**와 **그것을 쓰지 않는다는 정책**을 분리해 고정한다.
  둘을 섞으면 "못 한다"와 "안 한다"가 다시 뒤섞인다.

## 1. 맥락 — G3 논의 전체가 잘못된 축에서 돌고 있었다

G3("임무를 기체까지 보내는 공식 경로가 없다")는 2026-08-14~15 두 차례 조사 내내
**DJI Cloud API** 축에서만 다뤄졌다. 그 조사(`docs/dji/12`)의 결론은 좁게는 옳다 —
Cloud API의 Wayline Management 문서는 `dock-to-cloud/` 아래에만 있고
`pilot-to-cloud/` 아래에는 없다.

문제는 그 결론에서 **"그러므로 Dock 없이는 서버가 계획한 임무를 무인 실행시킬 방법이
없다"** 로 넘어간 추론이다. 이 추론은 **PSDK(온보드) 축을 아예 보지 않았다.**

2026-08-15 실측: `WaypointV3`·`UploadKmz` 라는 문자열은 이 저장소의 문서·목표
원장·`edge/` 코드 어디에도 **한 번도 등장한 적이 없다.** PSDK 원본을 2026-08-03에
받아 핀까지 걸어놓고(`edge/third_party/PSDK_LOCK.yaml`), 그 안의 임무 실행 API를
아무도 열어보지 않은 채 "경로가 없다"고 결론냈다.

## 2. 실측 — 온보드 임무 실행 경로는 존재한다 (1차 근거)

핀된 PSDK 3.16.0(`pinned_commit: 9af0853…`, MIT) 원문:

| 사실 | 근거 |
|---|---|
| KMZ 바이트를 기체에 업로드하는 함수 | `psdk_lib/include/dji_waypoint_v3.h` — `DjiWaypointV3_UploadKmzFile(const uint8_t *data, uint32_t dataLen)` |
| 그 임무를 시작/중지/일시정지/재개시키는 함수 | 같은 헤더 — `DjiWaypointV3_Action(E_DjiWaypointV3Action)` |
| START 한 번이 **시동 → 이륙 → 임무비행 → 착륙**까지 간다 | `samples/sample_c/module_sample/waypoint_v3/test_waypoint_v3.c` — START 이후 비행상태를 `STOPED → ON_GROUND(모터 회전) → IN_AIR → ON_GROUND` 로 순서대로 기다린다 |
| 입력 KMZ는 **Pilot 이 내보내는 것과 같은 형식**을 권장 | 같은 파일 주석: *"suggest use the exported kmz file by DJI pilot"* |
| M4D는 PSDK가 아는 기종이다 | `psdk_lib/include/dji_typedef.h` — `DJI_AIRCRAFT_TYPE_M4D = 1000`, `DJI_AIRCRAFT_SERIES_M4D = 9` |
| WaypointV3 샘플에 **기종 분기가 없다** | 위 샘플 전체에 `aircraftType` 검사 없음(다른 샘플들은 M4D/M4TD 분기를 명시적으로 가진다) |
| 매니폴드는 PSDK 3.16.0의 1급 대상이다 | `README.md` — **기본 빌드 타깃이 Manifold 2 → Manifold 3 으로 변경**, rootless 설치·네트워크 어댑터·적응형 전력 항목 |

**로컬에서 확인하지 못한 것(정직하게 적는다)**: 핀된 PSDK 트리에는 **기능×기종
지원 매트릭스가 없다**(`doc/` 에는 코드 스타일·E-Port 회로도·간이 모델뿐). 따라서
"공식 매트릭스에 M4D + Manifold 3 → Waypoint Mission 지원으로 표시돼 있다"는 형태의
주장은 이 저장소 안에서 검증할 수 없다. 위 표가 말하는 것은 **API가 존재하고
샘플이 기종 분기를 두지 않으며 M4D가 알려진 기종이라는 것**까지다 — 그 이상은 §3.

즉 **`KSI 계획 → KMZ → Manifold 3 → PSDK → M4D 자동 실행`** 은 Dock 없이 성립
가능한 구조다. 그리고 이 저장소는 **그 KMZ를 이미 만든다**(`wpml.py`).

### 2.1 `docs/dji/12` 의 범위를 한정한다

그 문서의 조사 자체는 유효하며 철회하지 않는다. 다만 결론 문장
("Dock을 사지 않는 한 DJI 쪽에 그런 경로 자체가 없다")은 **Cloud API 축에 한정된
서술로 읽어야 한다.** 온보드(PSDK) 축은 그 조사의 대상이 아니었다.

## 3. 아직 확인되지 않은 것 — 능력이 있다는 것과 우리 것이 작동한다는 것은 다르다

헤더에 함수가 있다는 사실은 **그 기종에서 그 함수가 성공을 반환한다는 증거가
아니다.** PSDK는 미지원 기능에 `DJI_ERROR_SYSTEM_MODULE_CODE_NONSUPPORT` 를
반환하는 구조이므로, 지원 여부는 문서 대조가 아니라 **호출 1회로 판별된다.**

| # | 미확인 | 확인 방법 |
|---|---|---|
| U1 | M4D가 WaypointV3를 실제 지원하는가 | `DjiWaypointV3_Init()` 반환값 — SUCCESS냐 NONSUPPORT냐 (읽기 수준, 비행 불필요) |
| U2 | **우리가 만든** KMZ를 기체가 받아들이는가 | `UploadKmzFile` 반환값. 우리 WPML은 실기 대조가 0회다(H4) |
| U3 | 실행에 RC/Pilot 측 권한·모드 전제가 있는가 | 실기 세션 관측 |
| U4 | Dock + Manifold 3 병용이 가능한가 | `docs/dji/11`은 "Dock 3 + M4D/M4TD는 서드파티 페이로드 미지원"이라 적었으나 **인용 URL이 없다** — 재확인 대상. 사실이라면 Dock 도입은 매니폴드를 잃는 선택이 된다 |

**U1~U3은 첫 실기 세션에서 비행 없이 대부분 판별된다.** 이것이 이 ADR이 지금
코드를 짜지 않는 이유다.

### 3.1 U1 판별 절차 — D3 게이트와 충돌하지 않게 (안전 필수)

D3이 `DjiWaypointV3_*` 를 금지하므로 **KSI 소스에 이 확인을 넣을 수 없다.** 대신:

1. **DJI 공식 샘플 트리에서만 실행한다.** 게이트의 스캔 대상은 `edge/psdk-app/src`·
   `edge/psdk-tap/src`·`edge/manifold-runtime/{src,include}` 이며 벤더 샘플은
   대상이 아니다. KSI 산출물은 깨끗한 채로 남는다.
2. **`DjiWaypointV3_Init()` 반환값만 본다.** 공식 샘플의
   `DjiTest_WaypointV3RunSample()` 을 **그대로 돌리면 안 된다** — 그 함수는 Init
   다음에 KMZ 업로드와 `Action(START)` 까지 이어져 **실제로 이륙을 시도한다.**
   `UploadKmzFile`·`Action` 은 호출하지 않는다.
3. **프로펠러를 제거한 상태에서 수행한다.** 2번을 지켰다면 기동 명령이 없지만,
   순서 실수 하나가 이륙 시도가 되는 표면이므로 물리적으로 막아둔다.
4. U2(우리 KMZ 수용 여부)는 U1이 SUCCESS일 때만 의미가 있고, **업로드는 실제
   기동 명령이 아니므로 분리해서 시도할 수 있다** — 다만 그것도 프로펠러 제거
   상태에서, `Action` 없이 업로드 반환값까지만 본다.

## 4. 결정

### D1 — 문서에서 "Dock 없이는 자율 실행 불가"를 삭제한다

정확한 서술은 이것이다:

> **Matrice 4D + Manifold 3 조합에는 PSDK 기반 온보드 임무 실행 능력이 존재한다.
> KSI는 그것을 아직 쓰지 않는다 — 실기 미검증이고, 안전정책으로 금지하고 있다.**

Dock은 **자율비행의 전제조건이 아니라 무인 상주 운영(자동 충전·반복 출격)의
인프라**다. 두 문제를 한 결정으로 묶지 않는다.

### D2 — 대표자 결정 대기 항목을 교체한다

- **폐기**: "Dock을 살 것인가" — 지금 답할 필요가 없는 질문이다.
- **신설**: **"KSI가 Manifold 3를 통해 기체를 직접 실행시키는 것을 허용할 것인가"**
  — 이것이 실제 갈림길이며, **FIELD-1 성공 이후에 판단한다**(§5).

> **[2026-08-16 대체 — ADR-KSI-021]** 대표자가 이 질문에 답했다 — 단, "허용/
> 불허" 이분법이 아니라 **단계적 개방(C2-S0~S4)**으로. D2·D3는 ADR-KSI-021이
> 대체한다. 아래 §5의 "PSDK-FLIGHT-EXECUTION-SPIKE는 FIELD-1 이후에만 연다"도
> 그 ADR의 단계 순서(§6)로 대체됐다 — S1(업로드만)은 FIELD-1을 기다리지 않고
> FIELD-0b 증거만으로 열린다.

### D3 — 안전 경계는 지금 넓히지 않는다. 오히려 **좁혀진 채로 실제로 강제한다**

> **[2026-08-16 갱신 — ADR-KSI-021]** 아래에서 닫은 두 구멍(빌드 자물쇠 자체의
> 결함)은 그대로 유효하다. 그 위에 **런타임 자물쇠**를 추가로 얹어 단계적으로
> 여는 구조는 ADR-KSI-021이 정의한다 — 이 절이 말하는 "넓히지 않는다"는 이제
> "빌드 자물쇠는 S2에서 멈추고, 그 이상은 서명 인가로만 연다"로 구체화됐다.

`check_shadow_flight_boundary` 게이트를 유지하되, 2026-08-15 실측으로 드러난
두 구멍을 닫았다:

1. **막고 있던 헤더 이름이 존재하지 않았다.** 게이트는 `dji_flight_control.h` 를
   찾았으나 PSDK의 실제 파일명은 `dji_flight_controller.h` 다 — header 층은 한
   번도 발화할 수 없었다(호출·심볼 층이 받쳐서 경계 자체가 뚫리진 않았다).
2. **`DjiWaypointV3_*` 는 어느 층에도 잡히지 않았다.** `DjiFlightController_` 만
   보는 게이트는 "KMZ 올리고 START" 두 줄을 그대로 통과시킨다 — 즉 "KSI 바이너리는
   기체를 못 움직인다"는 보증이 실제로는 성립하지 않고 있었다.

금지 대상을 실측 기준으로 다시 정의했다(`_FLIGHT_HEADERS`·`_MOTION_SYMBOL_PREFIXES`):
`DjiFlightController_*`(이·착륙·RTH·조이스틱), `DjiWaypointV2_*`·`DjiWaypointV3_*`(임무 실행),
`DjiInterestPoint_*`(선회 비행), `DjiFts_*`(비행종료장치).

**이것은 정책 변경이 아니라 원래 선언한 정책을 실제로 강제하게 만든 수정이다.**
회귀 시험은 핀된 PSDK 트리에 그 헤더들이 실제로 존재하는지까지 검사한다 — 없는
파일명을 막는 상태로 되돌아가지 않게.

> **FIELD-0 체크포인트.** 이 확대는 소스 스캔·파서 수준에서만 검증됐다(실기 ELF
> 없음). 실제 빌드 산출물 대상 재실행(`tools/edge/verify_flight_boundary_on_built_target.sh`)
> 은 FIELD-0 세션에서 해야 하며, PSDK static archive가 `DjiWaypointV3_*` 정의를
> 같은 object에 끌고 들어오면 **strict 층(`--require-zero-defined-symbols`)의 보고
> 심볼이 늘어날 수 있다.** 그것은 KSI 호출의 증거가 아니라 벤더 정의이므로 기본
> 실행의 실패 사유가 아니다 — `DjiFlightController_GetDjiErrorCode` 와 같은 취급이다.

### D4 — ADR-KSI-019 D4(자율성 경계표)는 유지하되 사유를 정정한다

| 주체 | 책임 | 변경 |
|---|---|---|
| KSI | 관측 필요성 판단 · 임무/경로 계획 · 실행 준비 | 유지 |
| 사람 | 비행 시작 전 승인 · 중단·통제권 회수 | 유지 |
| DJI 비행 시스템 | 승인된 임무의 실제 실행 | 유지 |

바뀌는 것은 **표가 아니라 그 표의 이유**다. "DJI가 그 경로를 안 열어줘서"가 아니라
**"열려 있지만 우리가 아직 검증하지 않았고, 검증 전에는 쓰지 않기로 해서"** 다.

### D5 — 정확도 서술을 상태 표현으로 바꾼다

ADR-KSI-016 D6의 결정(상대 비교로 시작, 절대 정확도 주장하지 않음)은 유지한다.
다만 그것을 **영구적 기술 한계로 서술하지 않는다.** 정확한 표현:

> KSI는 아직 독립 검사점 대비 절대 정확도를 현장에서 검증하지 않았다. 따라서
> 절대 정확도를 제품 성능으로 주장하지 않는다.

"기준점(GCP) 없이는 절대 정확도가 원리적으로 불가능하다"는 일반 명제로 쓰지
않는다 — RTK 기반으로 절대 정확도를 확보하는 워크플로는 존재하며, 우리가 아직
그것을 **검증하지 않았을 뿐**이다. 검증 경로는 이미 비어 있는 자리에 들어간다
(`ArtifactAccuracy(gcp_count, rmse, report_uri)`, ADR-KSI-016 D6).

**동시에 혼동하지 않는다**: 2026-08-12에 통과한 지오이드 대조(전국 10점, RMSE
0.0247m)는 **수직기준 변환 구현의 정확도**이지 사진측량 결과물의 정확도가 아니다.

### D6 — 구조물 이격·장애물 우회·동적 재계획의 미착수 사유를 정정한다

"기술적으로 불가능/금지"가 아니다. PSDK는 `dji_perception.h`(스테레오 인지 데이터)와
비행제어를 모두 공식 제공하므로 **기술적 가능성 자체는 있다.** 미착수 사유는
**DJI 온보드 안전기능과 중복되고, 현재 제품 목표 대비 복잡도·안전 책임이 과도하기
때문**이다. 문서 표기는 `NOT CURRENT PRODUCT SCOPE` 로 한다.

또한 "DJI가 알아서 다 피하므로 안전하다"고 쓰지 않는다 — DJI 자신이 환경 조건과
고속 이동 물체에 대해 회피 성능의 한계를 명시한다. 안전 층위는 셋으로 적는다:

```text
KSI Spatial Model   →  정적 사전 경로계획
DJI onboard         →  실시간 회피(성능 한계 있음)
사람                →  최종 중단·통제권 회수
```

## 5. 순서 고정 — FIELD-0 ~ FIELD-3

ADR-KSI-019 §5의 남은 항목(7번 실제 현장 검증, 8번 G6)을 다음으로 대체·세분한다.

> **[2026-08-15 2차 조사로 FIELD-0을 둘로 쪼갰다]** 매니폴드는 **첫 비행 폐루프의
> 필수 요소가 아니다** — 임무 전달은 사람의 KMZ 이관, 사진 회수는 SD카드 수동
> 오프로드(ADR-KSI-013 D1/D2), 재구성은 서버다. 유일한 접점은 커버리지 보고가
> `EDGE_DEVICE` 자격을 요구한다는 것뿐이다(`coverage_reports.py:491`, 그 외 403).
> 따라서 **2주째 막혀 있는 "매니폴드가 네트워크에 없다"가 첫 비행을 막을 이유가
> 없다.** FIELD-0a는 조종기만 있으면 오늘 할 수 있고, FIELD-1의 유일한 전제다.

| 단계 | 내용 | 비행 | 매니폴드 |
|---|---|---|---|
| **FIELD-0a** | 우리 KMZ를 Pilot 2가 임포트하는가 + Pilot 2가 내보낸 KMZ와 태그 대조 + **지상에서 사진 1장 찍어 EXIF로 실제 카메라 상수 확보** | **없음** | **불필요** |
| **FIELD-0b** | 매니폴드 전원·네트워크 → 앱 설치·기동 → PSDK 연결 → 기체 식별·텔레메트리 → §3 U1·U3 판별 → 확대 게이트 실기 재실행 | **없음(지상)** | 필요 |
| **FIELD-1** | KSI가 만든 매핑 계획 → Pilot 2 확인 → 사람 승인 → 웨이포인트 비행 → **실제 M4D 사진** → ingest → NodeODM → 실제 공간모델 | 1회 |
| **FIELD-2** | 그 모델의 설계 대비·변화 분석 → 재관측 영역 → KSI 계획 → 2회차 비행 → 모델 갱신 = **AOL 현장 실증** | 1회 |
| **FIELD-3** | 실제 DTM 기반 웨이포인트별 고도(지형추종) — `terrain.py` 를 KMZ 발급 경로에 배선 | 1회 | — |

> **[2026-08-26 대표자 개정]** FIELD-0a 이전 전면 신규 기능 동결은 폐기한다.
> Console·Synthetic Staging 이후 RC-first HIL을 먼저 준비하는 ADR-KSI-027 순서를
> 따른다. candidate adapter, HIL evidence 도구와 관련 결함 수정은 FIELD-0a 전에
> 구현할 수 있다. 이 개정은 비행 실행 권한을 넓히지 않는다. FIELD-1까지 실제
> 실행은 사람이 Pilot 2에서 승인·시작하는 기존 경로로 닫고, Waypoint `Action/START`,
> Virtual Stick, 이륙·경로·짐벌·카메라 제어는 별도 단계 게이트 없이는 금지한다.
> FIELD-0b는 FIELD-1과 **병렬**이며 서로의 전제가 아니다.

### 5.1 FIELD-3이 생각보다 가깝다 (2026-08-15 실측)

지형추종 배선을 막던 근거가 **실행 파일에는 해당하지 않는다.** 공식 샘플 KMZ를
풀어보면:

| 파일 | 웨이포인트 고도 표현 |
|---|---|
| `template.kml` (편집용) | `height` + `ellipsoidHeight` + `useGlobalHeight` |
| `waylines.wpml` (**기체가 실행**) | `executeHeight` 하나. `useGlobalHeight`·`ellipsoidHeight` **태그 자체가 없다** |

우리 `build_waylines_wpml` 은 **이미** 웨이포인트별 `executeHeight` 를 쓴다. 막는
것은 `_validate_route()` 의 균일고도 강제 하나이고, 그 근거로 적혀 있던
"ellipsoidHeight 를 계산할 수 없다"는 `template.kml` 쪽 얘기였다.

그리고 `executeHeightMode=relativeToStartPoint` 이므로 지형추종 명령값은
**두 표고의 차**다 — 같은 수직기준이면 상수항이 소거되어 **지오이드가 필요 없다.**

**PSDK-FLIGHT-EXECUTION-SPIKE**(D2의 신설 결정)는 FIELD-1 성공 이후에만 연다.
그때 §3 U1~U3 결과를 근거로 D3의 경계를 바꿀지 판단한다.

## 5.2 결정 대기 — 법적 상한과 DJI 고도 기준을 **분리**해야 한다

> **[2026-08-16 대표자 입력]** "이륙점 기준 150m"로 단순 확정하면 안 된다.
> 항공안전법 시행규칙의 비행승인 고도 기준은
> **① 일반 지역: 지표면·수면 또는 물건 상단으로부터 150m**,
> **② 사람·건축물이 밀집된 지역: 주변 최고 장애물 상단 기준**이다.
> 따라서 terrain-following 의 **법적 ceiling** 과 **DJI 내부 altitude reference** 를
> 분리해 설계해야 한다.
>
> (조문 원문 인용은 아직 이 저장소에 없다 — 근거 추적용으로 별도 확보 필요.
> 아래 설계 함의는 위 입력을 전제로 적는다.)

**지금 코드는 두 개념을 한 값에 겹쳐 놨다.** `FlightEnvelope` 는 이륙점 상대
150m 하나로 "DJI 가 해석하는 기준"과 "법적 상한"을 동시에 표현한다(ADR-KSI-011 D1).
**평지에서만 우연히 일치한다.**

| 축 | 기준면 | 성질 |
|---|---|---|
| 법적 상한 | 지표면·수면·물건 상단(일반) / 주변 최고 장애물 상단(밀집) | 규제 — 우리가 못 바꾼다 |
| DJI 고도 명령 | 이륙점 상대(`relativeToStartPoint`) | 기체 해석 규약 |

**지형추종은 이 분리를 요구하는 동시에 유리하게 작동한다.**

- 지형추종은 **지상고를 일정하게 유지**하므로 ①의 "지표면으로부터" 기준에 자연히
  부합한다. 오히려 지금의 고정고도 비행이 경사지에서 법적 기준을 넘길 수 있다.
- 반면 **이륙점 상대 상한은 경사지에서 잘못된 방향으로 작동한다** — 이륙점보다
  낮은 쪽에서는 법적으로 초과인데 통과시키고, 높은 쪽에서는 합법인데 거부한다
  (§5.3 이 고친 결함과 같은 뿌리다).
- ②의 "주변 최고 장애물 상단"은 **DSM 이 있어야 판정할 수 있다** — 우리가 이미
  만드는 산출물이다. 규제 판정과 제품 데이터가 만나는 지점이다.

**결정 대기 항목**(목표 원장 `decision-flight-ceiling-reference-split`):
`FlightEnvelope` 를 어떻게 쪼갤 것인가 — 법적 상한을 별도 필드로 둘지, 지역
구분(일반/밀집)을 현장 속성으로 받을지, DSM 기반 장애물 상단 판정을 발급
게이트에 넣을지.

**FIELD-3 착수 전에 확정한다.** 그 전까지는 현재 상한을 유지한다(보수적으로
막는 방향이라 안전하다).

## 5.3 같은 세션에서 고친 수직기준 결함

지형추종 계산기가 **절대표고**를 내면서 **이륙점 상대** 봉투와 직접 비교하고 있었다
(risk `terrain-altitude-vertical-reference-mismatch`). 양방향으로 틀렸다 —
표고 112m 현장에서 지상 30m 요청이 조용히 통과해 실제로는 지상 142m를 날고,
표고 130m 현장은 합법적인 30m 비행조차 영원히 거부됐다. 출력을
`commanded_height_m`(이륙점 상대, `executeHeight` 에 실리는 값)과
`absolute_elevation_m`(절대, DSM 여유값 전용)으로 분리해 닫았다.

**리뷰가 놓친 이유를 기록해 둔다**: 계약 시험이 `min/max` 두 필드만 흉내 내는 `Mock`
봉투를 써서, 봉투가 스스로 선언하는 `altitude_reference` 가 시험에 **나타나지도
않았다.** 대역이 "무엇을 비교하는지"를 가렸다. 지금은 실제 계약 모델을 쓴다.

## 6. 결과 — 알려진 대가

- **이 ADR은 "안 되는 줄 알았는데 되는 것"을 하나 열었고, 그만큼 유혹도 늘었다.**
  D3 게이트를 유지하는 비용은 "할 수 있는데 안 하는" 상태를 계속 설명해야 한다는
  것이다. 그 설명을 문서가 하지 않으면 다음 세션이 게이트를 결함으로 오인한다.
- **`docs/dji/12` 는 폐기되지 않는다.** Cloud API 축의 결론은 여전히 유효하고,
  서버→기체 원격 배포(사람이 현장에 없는 형태)를 원할 때 다시 필요하다.
- **U4(Dock + Manifold 병용 가부)가 미확인으로 남는다.** 사실이라면 Dock 도입은
  매니폴드 기반 온보드 지능을 포기하는 선택이 되므로, Dock 논의를 다시 열 때
  이 항목을 먼저 확인해야 한다.
- MASTER_PRD는 FROZEN이므로 수정하지 않는다(ADR 계층 누적, ADR-KSI-018 관례).
