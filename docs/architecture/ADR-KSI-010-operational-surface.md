# ADR-KSI-010 — S4 운영 표면: Evidence 스토리지 · 서명키 수명주기 · 보관 정책 집행

- 상태: ACCEPTED (2026-08-04, 대표자 승인 — 세 결정 일괄)
- 관련: ADR-KSI-002(Ed25519 서명 — 키 공급을 비범위로 남김),
  ADR-KSI-005(오프라인이 정상 동작·온라인은 가속),
  ADR-KSI-008(journal 영속·bearer 인증 — "서명키 공급 운영 ADR은 S4"),
  MASTER_PRD §22(대용량 미디어는 Presigned Upload),
  `contracts/schemas/retention-policy.v1.json`, INV-011(계약 서명)

## 맥락

goal `ops-serving-hardening`(S4)은 네 축을 요구한다 — Evidence 미디어 스토리지,
보관 정책 집행, 서명키 수명주기, journal 회전. 회전은 별도로 구현했고(commit
11ef369), 나머지 셋은 **서로 얽힌 인프라·보안 결정**이라 한 문서에서 정한다.

세 결정을 관통하는 제약은 하나다: **오프라인이 정상 동작이다**(ADR-KSI-005).
현장은 네트워크가 없거나 끊기는 게 예외가 아니라 기본이고, 그 상태에서도 증거
수집과 임무 발급이 계속돼야 한다. 이 제약이 아래 선택지 대부분을 탈락시킨다.

## 결정

### 1. Evidence 미디어 = 현장 내 S3 호환 스토리지(MinIO) + presigned URL

Core는 미디어 바이트를 **중계하지 않는다**. 업로드·열람 모두 Core가 짧은 수명의
presigned URL만 발급하고, Edge/브라우저가 스토리지와 직접 주고받는다.

기각한 대안:

- **Core 로컬 디스크 프록시** — presigned 개념이 성립하지 않고 Core가 대용량
  업로드 프록시가 된다. PRD §22가 명시적으로 배제한 구조이고, 단일 프로세스가
  영상 스트림을 받는 동안 안전 API(트리아지·임무 발급)의 응답이 함께 늘어진다.
- **클라우드 S3 직결** — 현장 네트워크가 끊기면 증거 업로드가 통째로 막힌다.
  "오프라인이 정상"과 정면 충돌한다. 게다가 건설 현장 영상의 국외 반출은 고객
  계약에서 걸릴 수 있는 사안이라 기본값으로 둘 수 없다.

따라서 **현장 서버에 함께 배포하는 S3 호환 스토리지**가 유일하게 두 요구를
동시에 만족한다. S3 API 를 쓰는 이유는 나중에 고객이 클라우드를 원할 때
엔드포인트 설정만 바꾸면 되기 때문이다 — 코드는 어느 쪽인지 알지 않는다.

- Core 는 `EvidenceStorage` 포트에만 의존한다. S3 호환 어댑터가 유일한 구현체이고,
  테스트는 그 포트의 가짜 구현으로 돈다(네트워크·컨테이너 없이).
- presigned URL 수명은 **분 단위**다. URL 자체가 인가이므로 길게 두면 그게 곧
  유출 창이다. 발급은 항상 권한 검사 뒤에 온다 — URL 을 아는 것과 권한을 가진
  것이 같아지지 않게, 발급 경로가 유일한 관문이다.
- 객체 키는 `sites/{siteId}/events/{eventKey}/{artifactId}` 로 **서버가 만든다**.
  클라이언트가 준 문자열을 키에 그대로 쓰면 경로 탈출·타 현장 덮어쓰기가 열린다
  (identifiers.py 의 경로-안전 검증과 같은 사고 — S2 재검토 P1 재발 방지).

### 2. 서명키 = 파일 공급 유지 + 회전·폐기 절차 명문화 (KMS 기각)

Mission Contract 서명키(Ed25519, INV-011)는 **로컬 파일에서 공급**한다. 권한
0600, 디스크 암호화는 배포 전제로 문서화한다.

기각한 대안:

- **클라우드 KMS** — 서명마다 네트워크 왕복이 필요하다. 오프라인 현장에서
  임무를 발급할 수 없게 되므로 제품 전제를 깬다. "온라인일 때만 발급"은
  ADR-KSI-005 가 배제한 운영 모델이다.
- **HSM/TPM** — 오프라인을 유지하면서 키를 보호하는 유일한 대안이지만 하드웨어
  조달·현장 서버 사양 확정이 선행돼야 한다. 파일럿 범위 밖으로 미룬다.

**지금의 진짜 결함은 키 저장 방식이 아니라 수명주기가 없다는 것이다.** 키가
한 번 만들어지면 회전도 폐기도 절차가 없고, 유출을 의심할 근거가 생겨도 할 수
있는 일이 정의돼 있지 않다. 그래서 이 ADR 이 정하는 것은:

- **키 식별자(kid)를 서명에 싣는다** — 검증자가 어느 키로 서명됐는지 알아야
  회전이 가능하다. 이미 `mission_signing_key_id` 로 조립에 들어와 있다.
- **회전 = 새 키를 활성으로 올리고 이전 키는 검증 전용으로 남긴다.** 발급은
  항상 활성 키 하나로만 한다(여러 키로 동시 발급하면 어느 것이 정본인지 잃는다).
- **폐기(revocation)는 발급 중단이 아니라 검증 거부다.** 이미 발급된 계약이
  기체에 남아 있을 수 있으므로, 폐기된 kid 로 서명된 계약은 **검증 시점에**
  거부돼야 한다 — 서버가 사라져도 로컬에서 유효한 계약이 살아있는 게 이 제품의
  설계(server loss must not invalidate a locally valid Mission Contract)라,
  폐기는 그 예외를 만드는 유일한 장치다.
- 회전 주기·트리거·보관 위치는 운영 문서(`docs/security/`)가 갖는다.

### 3. 보관 정책 집행 = tombstone (원장은 지우지 않는다)

`retention-policy.v1` 의 기간이 지나면 **미디어 객체를 삭제하고 원장에는 폐기
사실을 새 레코드로 남긴다**. 원장 레코드 자체는 수정도 삭제도 하지 않는다.

- append-only 원장에서 "지운다"는 성립하지 않는다. 과거를 고쳐 쓰는 순간
  감사 추적이 감사 대상이 된다.
- tombstone 레코드는 **무엇을·언제·어느 정책으로** 폐기했는지 담는다. "증거가
  없다"와 "증거를 정책대로 폐기했다"는 완전히 다른 사실이고, 사고 조사에서
  이 둘을 구분하지 못하면 원장의 값어치가 없다.
- 집행은 **명시적 실행**이다(자동 스케줄러를 Core 안에 두지 않는다). 데이터를
  지우는 코드가 아무도 부르지 않았는데 도는 것보다, 운영자가 부르는 편이 낫다.

**기본값(候補 30일 · 순찰 raw 90일 · 확정 이벤트 1095일 · 감사 1095일 · 텔레메트리
365일)은 스키마 그대로 쓴다.** 다만 이 값이 고객의 법적 의무와 맞는지는 확인되지
않았다 — 산업안전보건법상 보존 의무가 걸리면 1095일이 부족할 수 있고, 개인정보
최소보관 원칙에서는 30일도 길 수 있다. 스키마의 `customerOverrideAllowed` 가
이미 열려 있으므로 값 자체는 배포 시 정한다. **법적 검토는 이 ADR 의 범위 밖이며
별도 항목으로 원장에 남긴다.**

## 결과

- Core 의 새 의존: S3 호환 클라이언트(어댑터 안에만). 포트 경계 덕분에 테스트와
  다른 계층은 이 의존을 보지 않는다.
- 배포 단위가 하나 는다(현장 서버의 오브젝트 스토리지). 운영 문서에 반영한다.
- 임무 발급은 오프라인에서 계속 가능하다 — KMS 를 택했다면 잃었을 성질이다.
- 폐기된 증거는 "없음"이 아니라 "폐기됨"으로 조회된다.

## 미해결 (이 ADR 이 정하지 않는 것)

- 보관 기간의 법적 적정성 검토(별도 항목).
- HSM/TPM 도입 시점 — 현장 서버 사양 확정 이후 재검토.
- 스토리지 자체의 백업·복제 정책 — 현장 서버 백업 전략과 함께 정한다.
