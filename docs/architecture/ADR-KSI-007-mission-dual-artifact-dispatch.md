# ADR-KSI-007 — 임무 정의는 이원 산출물이다: 웨이포인트(WPML/KMZ) + Mission Contract

- 상태: ACCEPTED (2026-07-29, 대표자 확정)
- 관련: ADR-KSI-004(DJI 연동 이원화, Cloud API 연기), ADR-KSI-005(연결 아키텍처),
  ADR-KSI-006(온보드 활성화 트리거), FINAL_DECISION_LEDGER §하드웨어·자율성

## 맥락

"구역을 지정하고 임무 종류(순찰/매핑/점검)를 고르면 드론이 알아서 한다"는 UX
한 번의 행위가, 실제로는 소비자가 다른 두 산출물을 만들어야 한다는 게 이번
세션에서 명확해졌다. 지금까지는 이 둘을 "임무 하나"로 뭉뚱그려 논의해왔다.

## 결정

**임무 정의(구역+임무종류+정책)는 항상 두 개의 독립 산출물을 짝으로 발급한다:**

| 산출물 | 소비자 | 내용 | 전달 경로 | 발급 근거 |
|---|---|---|---|---|
| **웨이포인트 경로** | M4D (DJI Pilot 2 경유) | 실제 비행 좌표열 — coverage path(매핑=lawnmower, 순찰=외곽+관심점, 점검=근접) | **DJI WPML 표준 KMZ 파일**, Pilot 2 로컬 임포트(Cloud API 불요 — 공식 문서 확인) | 서버의 구역→경로 생성기 |
| **Mission Contract** | Manifold | 위험 판정 정책·Evidence 규칙·비행 봉투(FlightEnvelope)·유효기간(TTL) | edge-sync 계열 네트워크 경로(ADR-KSI-005) | 서버 서명 발급(기존 계약 스택) |

두 산출물은 **반드시 같은 site_frame·정책 버전(policy_version)으로 짝지어
발급**한다 — 하나만 갱신되고 다른 하나가 낡으면, 드론이 실제로 나는 구역과
Manifold가 판정 기준으로 삼는 구역이 어긋나는 사일런트 drift가 생긴다.

**재사용 모델**: KMZ는 파일이므로 구역·정책이 안 바뀌면 재생성 없이 여러 날
반복 사용한다("한 번 올리면 여러 날 반복"). 재전달이 필요한 시점은 구역/정책
변경 시뿐이다. 물리적 파일 전달 방법(USB/microSD 등)은 지금 확정하지 않는다 —
재전달 빈도가 낮아 부담이 작고, Dock 도입 시(ADR-KSI-004 Phase 5) Cloud API
경유로 자동화될 잔여 항목이다.

**이륙 트리거는 여전히 사람의 몫이다** — 매 비행마다 운용자가 RC Plus 2의
Pilot 2에서 임포트된 웨이포인트 미션을 선택하고 "시작"을 탭한다. 이는 DJI
네이티브 기능이며 우리가 구현하지 않는다(Dock 도입 전까지 물리·규제상 불가피한
사람의 마지막 관문 — 기존 결정 유지).

## 결과

- Core 서버의 "임무 정의" 기능 요구사항에 **WPML/KMZ 생성기**가 명시적으로
  추가된다 — 지금까지 "Mission Contract 발급"만 스코프로 인식했다면 누락이었다.
- 구역→경로 생성 로직(coverage path planning)은 KMZ 생성기의 입력이자, Mission
  Contract의 FlightEnvelope 산정 근거로 **한 곳에서 계산해 양쪽에 일관되게
  공급**한다 — 두 번 따로 계산하지 않는다(drift 방지).
- 실제 KMZ 파일 전달 자동화(파일을 RC Plus 2로 넘기는 물리/네트워크 경로)는
  본 ADR의 범위 밖으로 남기고, 필요 시점에 별도로 확정한다.
