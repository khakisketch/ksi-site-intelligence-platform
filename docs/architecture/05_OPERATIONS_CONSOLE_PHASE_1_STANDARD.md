# Operations Console Phase 1 제품·UX 구현 표준

- Status: Active implementation standard
- Date: 2026-08-24
- Authority: PRODUCT_CONSTITUTION, MASTER_PRD §7, ADR-KSI-024/025/026/027
- Requirements: REQ-UX-101, REQ-WRK-101, REQ-COP-101/102, REQ-SEC-101
- Invariants: INV-002, INV-040/041, INV-050/051, INV-060/061

## 1. 제품 문장과 역할

> KSI는 현장 데이터를 AI가 읽어 무엇이 달라졌고, 왜 중요한지, 지금 무엇을 결정해야
> 하는지를 근거와 함께 제시하고, 사용자의 결정을 다음 관측과 업무로 연결하는 제품이다.

| 사람 | 기본 화면 | 먼저 답해야 하는 질문 | 화면에 없는 것 |
|---|---|---|---|
| 다현장 책임자·경영진 | 홈 | 어느 현장을 왜 살펴봐야 하나 | 전체 작업 원장·비행 조작 |
| 현장 담당자 | 현장 작업공간 | 무엇이 달라졌고 무엇을 판단해야 하나 | 계약 ID 중심 동선 |
| 드론 운영자 | Pilot 2 | 승인된 비행을 어떻게 안전하게 수행하나 | KSI Console 업무 UI |

## 2. 정보 구조와 URL 규칙

전역 메뉴는 `홈 · 현장 · 작업 · 확인 항목`만 둔다. 모바일 하단은 같은 네 항목과
`더보기`를 둔다. `비행 임무 이력`, `장비 연결·지원 상태`, 전문가 복구는 운영 지원으로
내린다.

`/sites/{siteId}`는 다음 다섯 영역의 유일한 현장 작업공간이다.

1. **브리핑** — 변화, 중요성, 지금 검토할 결정 하나, 근거·관측 시점·불확실성, 저장형 AI 대화.
2. **현장 데이터** — 검증된 변화·상대 물량·정사영상·DSM·공간모델·설계 기준면·작업구역.
3. **확인 항목** — 현장에 필터된 발견, 근거 검토, 사람 판단, 이력.
4. **작업·조사** — WorkOrder, Acquisition progress, 원본·처리 상태, 발급된 비행 임무 이력.
5. **보고서** — 경영 요약, 현장 근거, 사람 결정, 다음 관측을 같은 서버 값으로 표현·내보냄.

Legacy `/missions`, `/assets`, `/world`, `/reports`, `/settings`, `/coming-soon/*`는 깨지지
않는다. Site/Mission을 식별할 수 있으면 해당 현장 영역으로 이동하고, 아니면 사람에게
현장을 선택하게 한다. 계약 ID를 첫 질문으로 삼지 않는다.

## 3. 화면 설계 규칙

### 3.1 사실·행동·카피

- 모든 핵심 화면은 하나의 기본 행동만 먼저 보여 준다. 기본 행동은 실제 조직 범위 원장과
  권한으로 계산하며, 없는 행동을 추측하지 않는다.
- 현장명과 사용자에게 필요한 판단을 기술 ID보다 먼저 보여 준다. 식별자, KMZ, digest,
  adapter receipt, 원시 전이 로그는 접힌 **전문가 복구 정보**에 둔다.
- 전역 메뉴에서 바로 도달하는 Home·현장·작업·확인 항목에는 `뒤로`를 두지 않는다. 상세는
  브라우저 이력을 추측하는 버튼 대신 `← 현장`, `← 작업`, `← 확인 항목`처럼 결정적인 부모
  작업공간을 가리키는 상단 맥락 링크를 쓴다. 등록·조사 Wizard는 자체 단계 이동을 소유한다.
- `이벤트`의 고객 용어는 `확인 항목`이다. 내부 Event 계약과 `/events` URL은 그대로다.
- `최근 관측`은 실제 관측 시점이 있을 때만 쓴다. 단순 `updatedAt`은 `최근 갱신`으로 부른다.
- `준비 완료`, `자동 진행`, `지원`, `정상`, `안전`은 근거가 있는 경우에만 쓴다. 장비 연결과
  처리 단계는 Home의 독립 카드가 아니라 관련 작업·운영 지원에서 표현한다.
- Core 조회 실패를 정상적인 0건과 같은 화면으로 바꾸지 않는다. 실패한 영역은 `알 수 없음`과
  재시도 경로를 표시하고, 다른 원장에서 성공한 영역은 계속 사용할 수 있게 둔다.
- 확인 항목 목록의 `근거 N건`은 삭제되지 않은 evidence artifact 수를 Core가 계산한 값이다.
  Dashboard는 그 수를 추측하거나 상세 조회 실패를 `근거 없음`으로 바꾸지 않는다.

### 3.2 공간·시각 규칙

- Console은 운영 surface다. 넓은 화면을 마케팅 hero나 좁은 중앙 문서로 쓰지 않는다.
- 기존 neutral 토큰, 타이포, 1px divider, 절제된 radius를 그대로 사용한다. 새 AI 보라색,
  과장된 대형 타이포, 깊은 그림자, WebGL/3D 장식, 가짜 현장 사진을 도입하지 않는다.
- 사진은 등록된 같은 현장의 evidence artifact일 때만 맥락 미리보기로 쓴다. 홈 캐러셀은
  카드 비교를 위해 이미지 슬롯의 비율을 유지하되, 사진이 없으면 실제 현장처럼 보이지 않는
  무채색 도식과 `관측 이미지 없음` 문구를 함께 표시한다. placeholder를 증거로 표현하지 않는다.
- Home은 안건 0건에도 큰 시각 영역을 유지하고 최근 현장 선택으로 전환한다. 그 아래에
  초기 설정 필요 현장, 최근 업데이트가 이어지는 순서를 유지하며, 텍스트 빈 상태가 큰
  시각 영역을 대체하지 않는다(ADR-KSI-025 D6).
- 카드의 목적은 다른 객체를 분리하는 것이지 모든 숫자를 감싸는 것이 아니다. 목록·표·divider를
  우선하고, 한 화면에 카드가 연속으로 붙어 보이면 한 surface로 합친다.
- 터치 타깃은 coarse pointer 44px 이상, fine pointer 36px 이상이다. `tap-target`과 기존
  input/button tokens를 사용하며 페이지별 임의 하한을 만들지 않는다.

### 3.3 반응형과 접근성

| 폭 | 표현 | 허용 행동 |
|---|---|---|
| 390 / 768 | 한 열, 현장 카드는 이름·상태·다음 확인·현장 열기 순서 | 조회, 확인 항목 분류, 분석 검토, Copilot 질의, 보고서 열람 |
| 1024 / 1440 | 비교표·현장 탭·전체 운영 surface | 역할이 허용한 WorkOrder/재관측/Mission/Site/복구 행동 |

SSR은 쓰기 행동을 보수적으로 숨긴다. 모바일에서 막힌 deep link는 빈 화면이 아니라
`노트북에서 계속` 이유를 표시한다. 일반 목록에서는 허용되지 않는 행동과 제약 안내를
함께 반복하지 않고, 사용자가 그 행동을 시작해야 하는 빈 상태·deep link에서만 한 줄로
알린다. 그 안내에는 개발자 구현 설명이나 권한 내부 구조를 반복하지 않는다. 키보드 focus,
색 외 라벨, reduced motion, 수평 page overflow 0은 필수다.

모바일 현장 작업공간은 선택한 영역 하나만 본문에 렌더한다. 브리핑에서 AOI 편집·공간모델·
시점·좌표계·관리 상태를 한꺼번에 이어 붙이지 않는다. AOI 편집은 `작업·조사`, 공간모델·
시점·좌표계는 `현장 데이터`가 소유한다. 실행할 수 없는 모바일 편집기는 비활성 버튼으로
보여 주지 않고, 사용자가 해당 영역을 연 경우에만 노트북에서 계속할 수 있음을 한 줄로 알린다.

## 4. 화면별 완료 정의

| Route | 목적 | 완료 판단 |
|---|---|---|
| `/` | 다현장 포트폴리오 입구 | 같은 현장이 상단 주의·최근 업데이트에 중복되지 않고, 현장명·사유·근거/맥락 링크가 보인다. 최근 업데이트가 0건이면 빈 섹션을 만들지 않는다. |
| `/sites` | 현장 선택·비교 | desktop은 비교표, mobile은 가로 스크롤 없는 현장 카드; 기술 ID와 World 단독 CTA는 기본 목록에 없다 |
| `/sites/{siteId}` | 현장 책임자의 판단 공간 | 헤더에 대상·실제 최신 관측·상태·한 행동이 있고 다섯 영역에서 사실과 근거를 잃지 않는다 |
| `/field` | 조직 전체 작업 큐 | 결정 필요·진행 중·완료가 현장명·필요 행동·갱신 시각으로 읽히며, 0건이면 중복 제한·복구 카드 없이 하나의 빈 상태만 보인다 |
| `/events` | 확인 항목 검토 | 현장·관측 내용·시점·근거 유무를 먼저 보여 주고, 0건·필터 없음이면 필터보다 빈 상태를 먼저 보이며 상세는 근거→KSI 관측→사람 결정→이력 순서다 |
| `/more` | 저빈도 운영 지원 | 지원 기능인지 미검증인지, 어떤 조건이 필요한지 정직하게 표시한다 |

## 5. AI와 상태 정직성

AI answer, briefing, citation, source watermark, uncertainty, missing data, provider/planner version은
감사 가능한 기록이다. 답변은 allowlisted tool call과 site-scoped citation을 모두 검증한 뒤
한 번에 저장한다. egress opt-in, provider 오류, 모르는 tool, 다른 현장의 citation, 근거 부족은
`BLOCKED` 답변과 사람이 취할 복구 안내로 표시한다.

Dashboard는 검증된 citation도 그대로 외부 URL로 열지 않는다. 허용된 Core resource path만
조직 범위 Console route로 변환하고, 알 수 없는 path는 출처 라벨로만 표시한다.

원본 이미지, presigned URL, object key, raw SQL, Mission 발급, 승인, 비행 좌표/명령은 AI
표면에 없다. UI/AI 테스트는 DJI capability, zero-touch 또는 closed-loop Field 증거가 아니다.

## 6. 변경 전 체크리스트

새 UX 작업은 다음을 모두 답한 뒤 구현한다.

1. 이 화면의 사용자와 단 하나의 기본 질문은 무엇인가?
2. 각 문구는 어느 조직 범위 원장/근거에서 왔는가? 불명확하면 어떻게 `알 수 없음`으로 보이는가?
3. 이 행동은 모바일에서 허용되는가? 아니면 노트북 안내가 필요한가?
4. 현장명·근거·사람의 결정이 기술 ID보다 먼저 보이는가?
5. 390/768/1024/1440, keyboard/focus/reduced-motion에서 어떻게 검증하는가?

HIL/실장비가 필요한 사실은 코드 주석·UI·acceptance에서 `NOT_VERIFIED`로 남기며, mock 또는
SDK header 존재를 지원 근거로 쓰지 않는다.
