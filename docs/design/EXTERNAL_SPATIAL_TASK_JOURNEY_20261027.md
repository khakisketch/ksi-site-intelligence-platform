# 외부 AI의 공간 작업 의뢰·영역 선택 흐름

상태: **초기 제안 뒤 Human이 bounded local 구현을 승인함(2026-10-27)**.
첫 구현은 기존 확정 작업구역·두 관측 사이 변화 분석과 Console 링크/동일 작업 재개다.
실제 구현·검증·남은 경계는 [기존 Console 작업 기록](../ledger/work/2026-10-26-console.md)이 소유한다.
아래는 경험 설계이며, 내장 지도 호스트 지원·새 구역 권한 확대·고객/배포 승인을 만들지 않는다.
현재 제품 권위와 외부 첫 분석의 범위는 `CONSOLE_CURRENT_SPEC.md`,
`API_FIRST_EARTHWORK_FIRST_REQUEST_CONTRACT.md`, ADR-KSI-037/038/039를 따른다.
이 문서는 운영 원장이나 다음 목표를 대체하지 않는다. 초기 조사 당시와 후속 구현을 구분한다.

## 해결할 문제

사용자는 DSM·CRS·좌표·작업구역 ID를 몰라도 질문할 수 있어야 한다. API 조회 이후의 작업 조립과
공간 선택을 고객이 다시 개발해야 한다면 제품 경험은 완결되지 않는다. KSI가 제공할 경험은
`질문 해석 → 필요한 의미만 확인 → 영역 선택 → 조건 점검 → 계산/데이터 준비 → 결과와 지도 검토`다.
외부 AI는 이 흐름을 조율하지만 경계·권한·측정 사실의 권위가 되지 않는다.

## 질문의 의미를 먼저 구분한다

| 사용자 표현 | 작업 의미 | 필요한 근거 / 현재 구분 |
|---|---|---|
| 지난번보다 얼마나 파고 쌓았나 | 관측 사이 지형 물량 변화 | 두 관측의 적격 DSM·고정 구역·호환 조건. 현재 첫 분석 경로의 목적 |
| 설계까지 얼마나 남았나 | 현재 지형과 선택한 목표 설계면의 차이 | 최신 관측·정확한 설계 revision·해당 분석 계약 필요. 관측 간 변화로 대체하지 않음 |
| 오늘 얼마를 해야 하나 | 오늘의 작업 목표·계획 | 위 수량만으로 결정 불가. 작업계획·기한·작업 가능 조건 등이 필요하며 현재 첫 분석 결과를 오늘의 작업 지시로 승격하지 않음 |

질문의 의미가 이미 명확하면 다시 묻지 않는다. 모호할 때만 기술 용어 대신 `최근 변화 / 설계까지 잔여량 /
오늘 작업 목표`처럼 작업 언어로 한 번 구분한다. 관측 시각은 제출·처리 시각과 구별하고,
날짜만 아는 자료에 임의의 시각을 만들지 않는다. 최신 관측이 오늘이 아니면 기준 날짜를 드러낸다.

## 영역은 세 경로로 선택한다

1. **명시적으로 공유한 현재 구역 재사용:** Console의 선택을 외부 AI에 전달하는 동작을 설계한다.
   다른 브라우저에서 열린 화면을 AI가 자동으로 안다고 가정하지 않는다.
2. **기존 이름 있는 작업구역 선택:** 현재 권한 안의 구역 후보를 이름·경계 미리보기로 제시한다.
   `동측`이 여러 구역에 해당하면 고르게 한다. 등록된 이름이나 방위 근거가 없는 영역을 꾸며내지 않는다.
3. **새 범위 지도 지정:** 실제 공간참조가 있는 허용 자료 위에서 사용자가 선택하거나 그린다.
   좌표 변환·경계 유효성·권한 범위는 서버에서 검증하고, 새 구역 확정은 기존 권한·기기 제약을 따른다.
   공개 표시용 크롭이나 스크린샷만 보고 실제 지리 경계를 확정하지 않는다.

AI의 공간 제안은 초안이다. 기존 확정 구역을 바꿔 쓰지 않는다. 범위를 바꾸면 기존 방식대로 새 구역을
등록/참조하며 과거 결과의 경계는 보존한다. 기존 승인 구역·규칙을 쓰는 보통의 반복 요청에는
매번 새 경계 승인 절차를 만들지 않는다. 데이터 준비의 사각형 외접 범위와 실제 분석 구역도 구분한다.

## 외부 환경별 상호작용

| 환경 | 제안 경험 | 필요한 추가 작업 |
|---|---|---|
| UI 확장을 협상·지원하는 MCP 호스트 | 대화 안의 KSI 지도 UI에서 영역 확인, 서버가 확정한 구역 참조를 대화로 반환 | KSI UI 리소스·선택 도구·보안 계약과 특정 호스트 검증. 현재 구현 완료 아님 |
| CLI 등 지도 UI가 없는 호스트 | `지도에서 영역 선택` 링크로 KSI Console의 좁은 선택 화면 열기 → `이 구역으로 계속` → 외부 작업이 확정 참조를 조회하여 재개 | 중단/재개와 연결 계약. 토큰·원시 저장소 키를 URL이나 대화에 넣지 않음 |
| 이름으로 구역을 고를 수 있는 텍스트 환경 | 허용된 기존 작업구역 후보를 골라 바로 진행 | 후보 탐색과 작업 맥락 도구가 필요. 임의 좌표 입력을 기본 UX로 요구하지 않음 |

MCP Apps는 MCP 자체와 별개의 선택적 UI 확장이다. 호스트의 capability를 확인한 뒤 지원하는 경로만 쓴다.
Codex 전체나 모든 MCP 클라이언트에 지도 위젯이 뜬다고 주장하지 않는다. 첫 제공은 하나의 선택한
외부 호스트와 Console 연결 경로를 실제로 검증하고, 내장 지도는 가능한 호스트에 추가하는 편이 보수적이다.

## 하나의 작업으로 이어지는 상태

지도에서 돌아왔을 때 좌표를 복사하거나 질문을 다시 작성하지 않는다. 제안하는 작업 맥락은
인증된 현장, 작업 의도, 확정 구역 참조/경계 식별, 입력 관측·자료 revision, 필요한 경우 선택한 설계면,
자료 기준 시점, 준비/계산 작업 ID를 연결한다. 이는 조율 상태이지 별도 구역/계산 권위가 아니다.

상태 예: `의도 확인 필요 → 영역 확인 필요 → 조건 점검 → 실행 가능/보완 필요 → 진행 중 → 결과 검토`.
영역·관측·기준면이 달라지면 조건을 다시 점검한다. 권한·AI 반출 동의는 서버가 매 호출에 확인하고,
선택 링크나 이전 준비 결과를 권한 증명으로 쓰지 않는다. 재시도는 같은 요청 식별자로 중복 실행을 피한다.
중단 후에는 이미 선택한 범위·자료와 남은 행동을 보여주며 만료·권한 상실 시 허용된 부분만 복구한다.

사용자가 마지막으로 확인할 요약은 `대상 구역(지도) / 무엇과 무엇을 비교하는지 / 자료 기준 날짜 /
계산 목적 / 제한`이다. 좌표·DSM·CRS를 사용자에게 직접 조립시키지 않는다. 조건 부족은 raw API 오류 대신
`설계면을 선택하면 잔여량을 확인할 수 있음` 등 해당 목적의 구체적 다음 행동으로 돌려준다.
지원하지 않는 작업을 다른 계산으로 몰래 대체하지 않는다.

## 결과와 다음 관측

결과는 숫자만 아니라 실제 사용 경계, 유효/제외/미확인 범위, 입력 날짜와 근거, 정량 제한을 함께 보인다.
외부 대화와 Console은 동일한 Core 결과를 가리킨다. 모르는 영역을 0으로 채우거나 AI가 수량을 추정하지 않는다.
구역을 눌러 원본/두 시점/변화 레이어를 검토하고, 다음 관측에는 같은 구역·규칙을 재사용한다.
새 자료에는 새 조건 점검과 새 결과가 필요하다. 공식 발행·기준 변경과 일반 계산 완료는 별개다.

## 구현 승인 전 조사에서 확인한 공백 (역사적 기준선)

현재 확인한 소스:
- Console은 `work-areas/WorkAreaPanel.tsx`와 `AoiPolygonMap`으로 구역 선택/등록을 다룬다.
  `src/lib/core-api/workAreas.ts`는 등록 시 기하를 고정하고 변경은 대체 등록으로 다룬다.
- Analysis MCP는 명시적 Site/WorkArea와 관측 선택자를 받아 조건 점검·분석·결과/근거 조회를 제공한다.
- Spatial Data MCP도 기존 Site/WorkArea와 사각형 요청 범위를 필요로 한다.
- 두 MCP의 현재 도구 목록에는 자연어 영역 해소, 지도 선택 요청, 외부 호스트 복귀 도구가 없다.

이는 **구현 승인 전**의 공백이다. 후속 additive task API/MCP·Console 연결은 기존 작업 기록을 따른다.
추가할 제안은 (1) 작업 의도·허용 작업 안내, (2) 범위가 제한된 구역 후보/선택, (3) 지도 선택과 외부 작업의
중단·재개 연결, (4) 지도 포함 결과 검토다. 새 서버 계약·권한·상태 전이는 별도 설계·검증이 필요하다.
소프트웨어 구성요소 존재는 실제 호스트·고객·현장·정량 인수 증거가 아니다.
